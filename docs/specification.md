# Спецификация системы Corporate

Corporate: корпоративный ИИ-ассистент с поиском по базе знаний компании (RAG) и админ-панель к нему. Документ описывает то, что реализовано в коде репозитория. Устройство системы и схемы взаимодействия компонентов: [architecture.md](architecture.md). Реализационные спецификации по компонентам (контракты API, модель данных по полям, экраны админ-панели, алгоритмы RAG и DLP, развёртывание), по которым систему можно воссоздать, — в каталоге [specs/](specs/README.md).

## 1. Назначение и цель

Сотрудники компании работают с языковыми моделями через единый чат, а ответы строятся с опорой на внутренние документы: регламенты, инструкции, описания процессов. Администрация управляет доступом, ограничивает расходы на модели и следит за использованием.

Цели системы:

- дать сотруднику чат с несколькими моделями за одним OpenAI-совместимым провайдером;
- отвечать на вопросы по документам компании с указанием источников и с учётом того, какие разделы базы знаний доступны отделу сотрудника;
- не отправлять модели чувствительные данные (ключи, реквизиты, паспортные данные);
- учитывать стоимость каждого вызова модели и ограничивать расход по сотруднику и отделу;
- вести сотрудников и отделы в одном месте и синхронно заводить учётные записи в едином входе (Keycloak).

Система состоит из трёх частей.

| Часть | Каталог | Назначение |
|---|---|---|
| Чат и сервер ассистента | `ai/` | Веб-чат, API, RAG, лимиты, DLP, память, генерация картинок, экспорт файлов. Форк LibreChat (MIT) с корпоративными доработками |
| Админ-панель | `admin-ui/` | Веб-интерфейс администратора и руководителей отделов |
| Сервис сотрудников | `admin-api/` | Справочник сотрудников и отделов на Go, зеркалирует учётные записи в Keycloak |

## 2. Пользователи и роли

### 2.1. Два уровня ролей

Права задаются в двух местах, и их нужно различать.

1. **Справочник сотрудников (`admin-api`)**. У сотрудника есть два признака: «Админ» (`is_admin`) и «Руководитель отдела» (`is_head`). Признак руководителя возможен только у сотрудника с отделом. Они определяют, что человек может делать с записями сотрудников и отделов.
2. **Сервер ассистента (`ai/`)**. У пользователя есть роль LibreChat: `OWNER`, `ADMIN`, `HEAD`, `USER`. Роль определяет доступ к админ-панели и набор полномочий (capability).

Связь между уровнями:

- признак «Админ» из справочника переносится в роль `ADMIN` на стороне ассистента при синхронизации справочника; снятие признака возвращает роль `USER`;
- роль `HEAD` на стороне ассистента назначает администратор запросом `PATCH /api/office/admin/users/:id/ai-role` (допустимы значения `HEAD` и `USER`). В админ-панели этот запрос не вызывается, а синхронизация справочника признак `is_head` в роль `HEAD` не переносит (см. раздел 7);
- при смене отдела роль `HEAD` сбрасывается в `USER`.

### 2.2. Роли

| Роль | Кто это | Что может |
|---|---|---|
| Сотрудник (`USER`) | Любой пользователь с активной учётной записью | Чат, поиск по доступным разделам базы знаний, свои проекты и документы, память, картинки, экспорт файлов, заявка на повышение лимита. В админ-панель не входит. Загрузка в базу знаний возможна, если администратор или руководитель включил сотруднику право `canUploadKnowledge` |
| Руководитель отдела (`HEAD`) | Сотрудник с отделом и ролью `HEAD` | Вход в админ-панель в пределах своего отдела: просмотр сотрудников отдела, расходов отдела, рассмотрение заявок на лимит, разделы базы знаний и документы своего отдела, выдача подчинённым права загрузки и доступа к разделам |
| Администратор (`ADMIN`) | Сотрудник с признаком «Админ» | Полный доступ к админ-панели: сотрудники, отделы, настройки AI, промпты, модели, лимиты, база знаний, расходы, аналитика, обратная связь, память |
| Владелец (`OWNER`) | Роль LibreChat | Всё, что может администратор, плюс право назначать роль `OWNER`; администратор может назначать роли `ADMIN`, `HEAD` и `USER`. Справочником сотрудников не назначается |

Заблокированный сотрудник (`blocked`) не может войти ни в один сервис: админ-панель и справочник отвечают ему 403, чат отвечает ошибкой блокировки, активные сессии в Keycloak завершаются при блокировке.

### 2.3. Полномочия руководителя отдела на стороне ассистента

Набор грантов роли `HEAD` задан в коде (`HEAD_CAPABILITIES`):

| Полномочие | Смысл |
|---|---|
| `access:admin` | Вход в админ-панель |
| `read:users` | Список и карточки сотрудников |
| `read:usage` | Журнал расходов |
| `manage:knowledge_documents` | Разделы и документы базы знаний |
| `manage:department_members` | Настройки подчинённых |
| `manage:limit_requests` | Заявки на повышение лимита |

Роли `ADMIN` и `OWNER` получают все полномочия при старте сервера. Полномочие отвечает на вопрос «что можно», а «над кем» решает обработчик по отделу вызывающего (`departmentScope`): руководитель видит и меняет только данные своего отдела; руководитель без отдела получает отказ.

### 2.4. Матрица прав в админ-панели

Знак «+» означает полный доступ, «свой отдел» означает ограничение отделом руководителя, «–» нет доступа. Столбец «Сотрудник» везде «–», потому что в админ-панель сотрудник без роли `HEAD` или `ADMIN` не входит.

| Раздел и действие | Администратор | Руководитель отдела |
|---|---|---|
| Сотрудники (общие данные), вкладка «Общие» | + | – (вкладка видна только администратору, см. 2.5) |
| Отделы (название, описание) | + | – |
| Настройки AI сотрудников: просмотр списка и карточек | + | свой отдел |
| Настройки AI сотрудника: лимиты, модели, модель по умолчанию | + | – |
| Настройки AI сотрудника: право загрузки в базу знаний, доступ и запрет разделов | + | свой отдел, кроме себя |
| Настройки AI отделов: промпт, модели, лимиты | + | – |
| Заявки на лимит: просмотр | + | свой отдел |
| Заявки на лимит: одобрить, отклонить | + | свой отдел, не выше лимита отдела |
| Промпты и общие настройки (глобальный промпт, модели, лимиты по умолчанию, возможности моделей) | + | – |
| База знаний: разделы | + | создание и правка только для своего отдела |
| База знаний: документы (загрузка, замена версии, архив, удаление, переиндексация) | + | разделы своего отдела |
| Расходы: журнал запросов с перепиской | + | свой отдел |
| Расходы: баланс провайдера | + | – |
| Аналитика | + | в интерфейсе скрыта; маршрут сервера при прямом обращении отдаёт данные только своего отдела |
| Обратная связь | + | – |
| Память: права ролей | + | – |

### 2.5. Матрица прав сервиса сотрудников (`admin-api`)

Права проверяются на сервере по признакам в справочнике. «Свой» означает сотрудника того же отдела.

| Действие | Сотрудник | Руководитель отдела | Администратор |
|---|---|---|---|
| Прочитать свою запись (`GET /admin/v1/me`) | + | + | + |
| Подтвердить своё имя, загрузить и удалить своё фото | + | + | + |
| Список и карточка сотрудников | – | свой отдел | + |
| Пригласить сотрудника | – | только в свой отдел | + |
| Повторное приглашение | – | свой, кроме админов и руководителей | + |
| Изменить должность | – | у своего | + |
| Изменить почту, имя, отдел, признаки «Админ» и «Руководитель», блокировку | – | – | + |
| Удалить сотрудника | – | только не вошедшего своего, кроме админов и руководителей | + |
| Сбросить пароль (временный пароль) | – | – | + |
| Удалить чужое фото | – | – | + |
| Список отделов | – | + | + |
| Создать, изменить, удалить отдел | – | – | + |
| Журнал действий | – | – | + |

Сервер не даёт снять права у последнего активного администратора, снять признак «Админ» с самого себя и заблокировать самого себя. Интерфейс раздела «Сотрудники» в админ-панели виден только администратору, поэтому права руководителя из этой таблицы доступны через API, но не через текущий интерфейс.

## 3. Функциональные требования

Требования пронумерованы в формате `<модуль>.<номер>`.

### 3.1. Вход и учётные записи (AUTH)

| № | Требование |
|---|---|
| AUTH.1 | Вход в чат и админ-панель выполняется через Keycloak (OpenID Connect, authorization code с PKCE). Форма локального пароля отключена, `/api/auth/login` отвечает 403 |
| AUTH.2 | Самостоятельная регистрация отключена; учётные записи создаёт администратор через справочник сотрудников |
| AUTH.3 | Сотрудник входит по одноразовой ссылке-приглашению (magic link, срок жизни по умолчанию 7 суток), после чего сам задаёт пароль. Письмо уходит из Keycloak; если письмо не отправилось, ссылку можно передать вручную |
| AUTH.4 | При выходе из чата завершается и сессия в Keycloak |
| AUTH.5 | Админ-панель использует отдельный клиент Keycloak (`admin`); сервер ассистента и `admin-api` принимают токен только с ожидаемым клиентом (`azp`) и аудиторией |
| AUTH.6 | Пользователь ассистента создаётся при первом обращении или при синхронизации справочника, с привязкой к `sub` из Keycloak и идентификатору сотрудника |
| AUTH.7 | Блокировка проверяется на каждом авторизованном запросе (кэш 30 с, сбрасывается при правке администратором). Заблокированному отказывается чат, а при блокировке в справочнике сессии в Keycloak завершаются |

### 3.2. Чат и модели (CHAT)

| № | Требование |
|---|---|
| CHAT.1 | Чат работает через OpenAI-совместимый провайдер. Поддерживаются два провайдера, выбор задаётся переменной `AI_PROVIDER` (`openrouter` или `polza`): от неё зависят эндпоинт моделей, баланс в админке и валюта стоимости вызова |
| CHAT.2 | Модели показываются под именами из `modelSpecs`: GPT-5.6 Luna (по умолчанию), Gemini 3.7 Flash, Claude Sonnet 5. Выбор принудительный (`enforce`): сотрудник выбирает только из списка. Кроме именованных, в выбор попадают разрешённые администратором модели из каталога провайдера |
| CHAT.3 | Список разрешённых моделей и модель по умолчанию вычисляются по цепочке сотрудник, отдел, глобальные настройки. Пустой список на уровне означает «не задано здесь», а не «запрещено все» |
| CHAT.4 | Системный промпт собирается из глобального и промпта отдела: промпт отдела добавляется после глобального и не заменяет его |
| CHAT.5 | Запрос с моделью, не разрешённой сотруднику, отклоняется |
| CHAT.6 | Заголовок беседы генерируется автоматически на языке запроса (не длиннее пяти слов) |
| CHAT.7 | Параллельные вызовы инструментов выключены (`parallel_tool_calls: false`): вызовы идут по одному |
| CHAT.8 | Вложения к сообщению: до 10 файлов, до 50 МБ каждый; изображения, PDF, Word, Excel, PowerPoint, OpenDocument, RTF, текстовые форматы |
| CHAT.9 | Интерфейс на русском и английском. Отключены агенты, MCP-серверы, расписания, навыки, общие ссылки, закладки, пресеты, временные чаты, запуск кода, редактирование сообщений и ветвление |
| CHAT.10 | Сотрудник может поставить ответу оценку (палец вверх или вниз) с причиной и комментарием |

Возможности модели (база знаний, веб-поиск, память, экспорт файлов, генерация картинок) включаются флагами в `modelSpecs`; для базы знаний и веб-поиска администратор может переопределить флаги и подписи моделей (раздел «Промпты и общие настройки»).

### 3.3. База знаний и RAG (KB)

Корпоративные документы организованы по **разделам** (spaces). Раздел имеет название, описание, список разрешённых отделов и флаг «Включено».

| № | Требование |
|---|---|
| KB.1 | Раздел: название (уникальное), описание, разрешённые отделы, флаг включения. Пустой список отделов означает «доступен всем отделам». Выключенный раздел не участвует в поиске и скрыт от сотрудников |
| KB.2 | Раздел можно удалить, только если в нём нет документов |
| KB.3 | Документ имеет название, описание, файл, источник, владельца, версию, дату актуальности и статус: `active` (действующий), `draft` (черновик), `archived` (архив) |
| KB.4 | Поддерживаемые форматы загрузки: PDF, DOCX, XLSX, PPTX, TXT, MD, CSV. Проверяются и расширение, и MIME-тип. Размер файла до 25 МБ |
| KB.5 | Загрузка новой версии указывает заменяемый документ (`supersedesId`): он должен быть в том же разделе, а у загружающего должно быть право распоряжаться им. После успешной загрузки заменяемый документ уходит в архив |
| KB.6 | Приём документа выполняется в фиксированном порядке: сохранение оригинала в объектное хранилище, извлечение текста через `rag-api`, проверка текста, индексация в pgvector, запись документа в базу. При сбое оригинал удаляется, запись в базе без индекса не создаётся |
| KB.7 | Документ отклоняется, если после извлечения текст нечитаем (более 5% управляющих символов), короче 200 символов (для TXT, MD, CSV короче 20) или длиннее 15 млн символов. Причина возвращается пользователю по-русски |
| KB.8 | Оригиналы хранятся в S3-совместимом хранилище (MinIO, бакет `knowledge`); если хранилище не настроено, сервер пишет оригиналы на диск |
| KB.9 | Переиндексация раздела заново отправляет все его документы в индекс и возвращает список пропущенных с причиной (нет сохранённого оригинала, сбой этапа) |
| KB.10 | Поиск гибридный: плотный (эмбеддинги в pgvector через `rag-api`, модель `baai/bge-m3`, по одному запросу на раздел, `k = 5`) и лексический (текстовый индекс MongoDB по названию и тексту с русской морфологией, до 20 документов). Результаты сливаются методом RRF на уровне документа |
| KB.11 | Выдача фильтруется: абсолютный порог близости 0,45 и относительный порог 0,9 от лучшего результата; фрагменты короче 300 символов отбрасываются; не более 3 фрагментов с одного документа; не более 10 фрагментов в выдаче |
| KB.12 | Раздел доступен сотруднику, если он включён, не в списке запрещённых для сотрудника, и выполняется одно из условий: роль админ-уровня; у раздела нет ограничений по отделам; отдел сотрудника в списке разрешённых; раздел выдан сотруднику явно. Заблокированному недоступно ничего |
| KB.13 | Права записи отдельны от прав чтения. Администратор пишет в любой включённый раздел. Руководитель, а также сотрудник с правом `canUploadKnowledge`, пишут только в разделы, у которых свой отдел входит в список разрешённых |
| KB.14 | Сотрудник с правом записи редактирует и архивирует только свои документы; руководитель и администратор распоряжаются любыми документами доступного раздела. Безвозвратное удаление документа и создание, правка, удаление разделов доступны только руководителю (в своём отделе) и администратору |
| KB.15 | В чате доступны два инструмента: `knowledge_search` (поиск по разрешённым разделам) и `knowledge_list` (список доступных документов). Поиск закреплён в меню инструментов |
| KB.16 | Ответ ссылается на источники якорями вида `turn0fileN`, клиент превращает их в список источников с названием, версией и владельцем документа. Номер документа неизменен в пределах одного ответа |
| KB.17 | Режим «искать в документах» делает поиск обязательным: если ничего не найдено, модель должна сказать, что в документах компании этого нет, а не отвечать из общих знаний |
| KB.18 | Просмотр документа в чате (карточка с текстом и скачивание оригинала) доступен по тем же правилам, что и поиск |
| KB.19 | Индексация учитывается в журнале расходов отдельным сценарием (`kb_index`) |

### 3.4. Проекты и документы сотрудника (DOC)

| № | Требование |
|---|---|
| DOC.1 | Беседы можно группировать в проекты. К проекту сотрудник прикладывает свои документы (PDF, DOCX, XLSX, PPTX, TXT, MD, CSV), они видны только ему |
| DOC.2 | Ограничения: не более 20 документов в проекте, не более 200 МБ документов на сотрудника, файл не более 25 МБ |
| DOC.3 | Документы индексируются так же, как документы базы знаний (проверка текста, эмбеддинги в pgvector). Расходы на индексацию пишутся сценарием `doc_index` |
| DOC.4 | В запрос модели документы проекта попадают через бюджет контекста: небольшие документы целиком (до 6000 токенов суммарно), у остальных начало и найденные поиском фрагменты. Пороги релевантности для таких документов сняты, так как сотрудник приложил их сам |
| DOC.5 | Предыдущая реплика сотрудника используется для коротких уточняющих запросов (менее 15 символов) |

### 3.5. Защита данных, DLP (DLP)

| № | Требование |
|---|---|
| DLP.1 | Перед отправкой запроса модели чувствительные значения заменяются на заглушки, а в ответе (включая потоковый) заглушки восстанавливаются в исходные значения. Сотрудник видит и пишет исходные данные |
| DLP.2 | Категории: `secrets` (секреты и ключи), `payment_card`, `bank_account`, `ru_inn`, `ru_snils`, `ru_passport`. Для каждой задан режим `mask`, `shadow` (только фиксировать) или `off`; в поставке все шесть в режиме `mask` |
| DLP.3 | Модели в запросе добавляется указание переносить заглушки в ответ дословно |
| DLP.4 | Маскирование выполняется на уровне HTTP-запроса к провайдеру и покрывает основной чат и служебные вызовы (конспекты, сжатие памяти). Индексируемый текст маскируется при включённом `maskEmbeddings` |
| DLP.5 | При сбое модуля DLP запрос не отправляется (fail-closed), сбой записывается в журнал аудита |
| DLP.6 | Срабатывания пишутся в журнал аудита: категория, число совпадений, сокращённые хэши значений (не сами значения), пользователь, беседа, режим. Срабатывание на `secrets` имеет уровень critical |

### 3.6. Лимиты и расходы (LIM)

| № | Требование |
|---|---|
| LIM.1 | Каждый вызов модели записывается в журнал расходов: сотрудник, отдел, модель, токены запроса и ответа, стоимость в долларах, источник стоимости (`provider`, `estimate`, `unknown`), сценарий (обычное сообщение, генерация картинки `image_gen`, распознавание речи `stt`, индексация `kb_index` и `doc_index`, служебные вызовы) |
| LIM.2 | Стоимость берётся из ответа провайдера. Если провайдер считает в рублях (`polza`), стоимость пересчитывается в доллары по курсу `RUB_PER_USD`, задаваемому вручную |
| LIM.3 | Лимит один: расход в долларах за сутки (по времени часового пояса процесса, в поставке `Europe/Moscow`). Достижение порога блокирует дальнейшие запросы до начала следующих суток. Лимит по числу запросов и месячный лимит в системе не применяются |
| LIM.4 | Эффективный лимит вычисляется так: личный лимит сотрудника, если задан (пустое значение личного лимита означает «без ограничения», а не «взять из отдела»); иначе лимит отдела; иначе глобальный лимит по умолчанию |
| LIM.5 | Сотрудник видит свой расход за сутки и месяц и лимит (`GET /api/office/usage/me`) |
| LIM.6 | Сотрудник подаёт заявку на повышение суточного лимита с комментарием; одновременно у сотрудника может быть одна заявка в статусе «на рассмотрении» |
| LIM.7 | Администратор одобряет заявку с новым значением лимита или отклоняет её. Руководитель делает то же для своего отдела, но не может поднять лимит выше лимита отдела (с учётом глобального). Одобрение меняет только запрошенное окно |
| LIM.8 | Превышение лимита и блокировка возвращаются сотруднику читаемым сообщением с временем сброса |

### 3.7. Память (MEM)

| № | Требование |
|---|---|
| MEM.1 | Модель сама сохраняет сведения, полезные в следующих беседах, и выполняет явные просьбы «запомни» и «забудь». Отдельного агента памяти нет: записи идут встроенными вызовами по ходу ответа |
| MEM.2 | Память разделена на личную (видна во всех чатах) и проектную (только в чатах проекта). Лимиты: запись до 2000 символов, раздел до 12000 токенов |
| MEM.3 | Когда запись поднимает раздел выше 90% лимита, он в фоне сжимается дешёвой моделью, не чаще раза в 6 часов. Снимок до сжатия хранится 30 дней; последнее сжатие можно отменить из панели памяти |
| MEM.4 | После бесед формируются краткие конспекты (до 600 символов); последние восемь попадают в запрос как блок «недавние беседы» |
| MEM.5 | Сотрудник может отключить память в настройках персонализации, если роль это разрешает |
| MEM.6 | Права ролей на память (использовать, создавать, читать, изменять и удалять, отключать у себя) задаёт администратор в разделе «Память» админ-панели |
| MEM.7 | Вызовы моделей для конспектов и сжатия пишутся в журнал расходов |

### 3.8. Генерация изображений (IMG)

| № | Требование |
|---|---|
| IMG.1 | Инструмент `generate_image` создаёт картинку по описанию (до 4000 символов) или правит до четырёх присланных либо ранее созданных картинок. Модель вызывает его только по прямой просьбе сотрудника |
| IMG.2 | Перед каждой генерацией сотрудник подтверждает её в чате: «одобрить», «изменить» (описание, формат) или «отклонить». Подтверждение настроено для `generate_image` в `toolApproval.ask`; остальные инструменты выполняются без подтверждения |
| IMG.3 | Форматы: 1:1, 16:9, 9:16, 4:3, 3:4, 3:2, 2:3; по умолчанию 1:1. Модель, разрешение и качество заданы в `imageGeneration` (в поставке `openai/gpt-5.4-image-2`, 1K, medium, JPEG) |
| IMG.4 | Перед подтверждением проверяются блокировка и остаток суточного лимита с учётом оценочной стоимости картинки (`estimatedCostUsd`); при нехватке остатка генерация отклоняется с пояснением, без показа сумм сотруднику |
| IMG.5 | Стоимость пишется в журнал расходов сценарием `image_gen`; в журнале администратор видит запрос к картинке и саму картинку |

### 3.9. Веб-поиск (WEB)

| № | Требование |
|---|---|
| WEB.1 | Инструмент `web_search` ищет в интернете и читает найденные страницы; поиск и чтение выполняет внешний сервис Tavily, переранжирование выключено |
| WEB.2 | Инструмент закреплён в меню и включается флагом `webSearch` модели |
| WEB.3 | Запросы к внешним сервисам и к провайдеру моделей могут идти через прокси, заданный секретом (`HTTPS_PROXY`); обращения к сервисам внутри кластера идут напрямую |

### 3.10. Голосовой ввод и экспорт файлов (VOX)

| № | Требование |
|---|---|
| VOX.1 | Кнопка микрофона записывает диктовку (WAV 16 кГц, моно, до 15 МБ), сервер расшифровывает её аудиомоделью и дописывает текст в поле ввода; отправляет сообщение сотрудник сам. Языки: русский и английский |
| VOX.2 | Распознавание идёт через `chat/completions` с частью `input_audio`; стоимость пишется сценарием `stt` и входит в суточный лимит. Озвучивание ответов выключено |
| VOX.3 | Инструмент `export_file` создаёт файл для скачивания: Word (docx), PDF, Excel (xlsx), CSV, PowerPoint (pptx), Markdown. Вызывается только по просьбе сотрудника; ограничения: до 100000 строк в таблицах, имя файла до 120 символов |

### 3.11. Админ-панель (ADM)

Панель разделена на две вкладки. Вкладка «Общие» (сотрудники и отделы) видна только администратору. Вкладка «AI» показывает только те разделы, на которые у пользователя есть полномочие (таблица ниже). Вход в панель требует токена Keycloak клиента `admin` и полномочия `access:admin` либо признака «Админ» в справочнике.

| Раздел | Полномочие | Что делает |
|---|---|---|
| Сотрудники | признак «Админ» (справочник) | Список с поиском и фильтрами по отделу и статусу (активен, приглашён, заблокирован, приглашение истекло); создание и приглашение с выдачей одноразовой ссылки; повторная отправка и отзыв приглашения; правка имени, почты, должности, отдела, признаков «Админ» и «Руководитель отдела», блокировки; сброс пароля (временный пароль показывается один раз); удаление. В собственной карточке недоступны признаки доступа, блокировка, сброс пароля и удаление |
| Отделы | признак «Админ» | Создание, правка названия и описания, удаление отделов; число сотрудников в отделе |
| Настройки AI сотрудников (`ai/users`) | `read:users` | Список сотрудников с ролью в AI, моделью, расходом и лимитом. Карточка: роль, разрешённые модели и модель по умолчанию, личный лимит, право загрузки в базу знаний, разрешённые и запрещённые разделы. Показ наследования значений от отдела и глобальных настроек |
| Настройки AI отделов (`ai/departments`) | `manage:configs`, маршрут только для администратора | Системный промпт отдела, разрешённые модели, модель по умолчанию, лимит отдела. Название и описание отдела приходят из справочника |
| Заявки на лимит (`requests`) | `manage:limit_requests` | Заявки сотрудников с фильтром по статусу, история изменения лимита, одобрение с новым значением и отклонение |
| Промпты и общие настройки (`prompts`) | `manage:prompts` | Глобальный системный промпт, разрешённые модели и модель по умолчанию, лимиты по умолчанию, возможности моделей (база знаний, веб-поиск, своё название и описание); обзор промптов отделов; справочник моделей провайдера с ценами и длиной контекста |
| База знаний (`knowledge`) | `manage:knowledge_documents` | Разделы и документы, загрузка и замена версии, архив, удаление, переиндексация раздела, индикатор «не проиндексирован» |
| Расходы (`spend`) | `read:usage` | Журнал расходов: один запрос сотрудника в одной строке, внутри вызовы модели (довызовы из-за инструментов, заголовок чата); фильтры по сотруднику, отделу, модели и периоду; переписка и сгенерированные картинки; остаток на счёте провайдера |
| Аналитика (`analytics`) | `read:insights` | Расходы, вызовы и токены с группировкой по сотруднику, отделу, модели, дню или сценарию; динамика по дням; активность. Вызовы с неизвестной стоимостью считаются отдельно |
| Обратная связь (`feedback`) | `manage:configs` | Оценки ответов за период с фильтром по знаку, причиной и комментарием |
| Память (`memory`) | `manage:roles` | Права ролей на память (см. MEM.6) |

Все списки с большим числом записей постраничные; интерфейс переключается между русским и английским, поддерживает светлую и тёмную темы.

### 3.12. Справочник сотрудников и отделов (DIR)

| № | Требование |
|---|---|
| DIR.1 | Сотрудник: имя, фамилия (может быть пустой), почта (уникальна среди неудалённых), должность, отдел, признаки «Админ» и «Руководитель отдела», блокировка, статус приглашения, фото |
| DIR.2 | Статус вычисляется: `blocked`, если заблокирован; иначе `active`, если задана дата активации; иначе `invite_expired`, если срок приглашения истёк; иначе `invited` |
| DIR.3 | Создание сотрудника создаёт в Keycloak учётную запись и одноразовую ссылку. При ошибке записи в базу созданная учётная запись удаляется (компенсация) |
| DIR.4 | Повторное приглашение пересоздаёт учётную запись входа: прежние ссылки перестают работать, идентификатор сотрудника сохраняется, а `sub` меняется. Потребители сопоставляют сотрудника по идентификатору, а не по `sub` |
| DIR.5 | Статус «приглашён» меняется на «активен», когда Keycloak сообщает, что пароль задан (проверка раз в 30 с по умолчанию) |
| DIR.6 | Изменение имени, почты или включённости учётной записи зеркалируется в Keycloak; блокировка завершает сессии |
| DIR.7 | Удаление мягкое. Почту неактивированного сотрудника меняет только повторное приглашение, а не правка |
| DIR.8 | Фото: JPEG или PNG до 5 МБ и 16 млн точек, хранится в базе, отдаётся по адресу с версией и заголовком вечного кэша |
| DIR.9 | Журнал действий: приглашение, повторное приглашение, изменение, удаление, сброс пароля, подтверждение имени, удаление фото, операции над отделами; в записи хранятся различия полей |
| DIR.10 | При любом изменении сотрудника или отдела сервис отправляет уведомление `POST {type, id}` серверу ассистента (токен клиента без ролей). Доставка не блокирует операцию |
| DIR.11 | Самолечение: раз в 5 минут сервис сверяет профили в Keycloak со справочником и исправляет расхождения. Порог безопасности: если за проход нужно выключить или включить больше 5 учётных записей, проход ничего не применяет |
| DIR.12 | Сервер ассистента получает сотрудников и отделы из справочника сервисным токеном (чтение), принимает уведомления и раз в минуту сверяет все данные. Синхронизация переносит имя, почту, должность, отдел, признак «Админ» и блокировку (при блокировке сессии удаляются). Режим задаётся `ADMIN_API_SYNC_MODE`: `off`, `report` (только отчёт), `apply`. Массовые опасные изменения (больше `ADMIN_API_SYNC_MAX_CHANGES`, в поставке 5, блокировок и снятий прав администратора) не применяются |
| DIR.13 | Команды сервиса: `serve`, `migrate`, `import` (разовый перенос сотрудников и отделов с режимом проверки без `--apply`), `set-heads` (разовая расстановка признака руководителя) |

## 4. Нефункциональные требования

### 4.1. Безопасность

- Аутентификация только через Keycloak (OIDC, PKCE). Токены проверяются по JWKS издателя; проверяются клиент (`azp`) и аудитория. Токен сервисного клиента не может вызывать маршруты человека, а токен человека не годится для маршрутов сервисов.
- Права проверяются на сервере: полномочие (capability) плюс ограничение по отделу в обработчике. Скрытие разделов в интерфейсе не заменяет серверных проверок.
- Блокировка действует немедленно: кэш статуса 30 секунд, при правке администратором сбрасывается; Keycloak завершает активные сессии.
- DLP маскирует чувствительные данные до выхода запроса за пределы кластера (раздел 3.5).
- Секреты (ключи провайдера, пароли баз, секреты клиентов Keycloak, ключи объектного хранилища) хранятся в секретах Kubernetes и не входят в манифесты.
- Журналы: журнал аудита DLP на стороне ассистента, журнал действий над сотрудниками и отделами в `admin-api`, журнал расходов с перепиской для администратора.
- Загрузки: проверка расширения и MIME-типа, лимиты размера, проверка читаемости извлечённого текста.
- Данные проекта (документы сотрудника) изолированы по владельцу.

### 4.2. Хранение данных

| Данные | Хранилище |
|---|---|
| Беседы, сообщения, пользователи, настройки AI, отделы (зеркало), политики, журнал расходов, метаданные базы знаний, память, проекты | MongoDB |
| Векторный индекс документов | PostgreSQL с расширением pgvector (база `ragdb`) |
| Оригиналы документов базы знаний | MinIO (S3), либо диск, если хранилище не настроено |
| Сотрудники, отделы, фото, журнал действий | PostgreSQL сервиса `admin-api` |
| Учётные записи и сессии входа | PostgreSQL Keycloak |
| Вложения и сгенерированные картинки | том сервера ассистента |

### 4.3. Развёртывание и масштабирование

- Целевая среда: Kubernetes, пространство имён `corporate`, один экземпляр каждого сервиса. Манифесты с ограничениями памяти приведены в [architecture.md](architecture.md).
- Состояние сервера ассистента вынесено в MongoDB, pgvector, MinIO и том, однако в поставке сервер, `rag-api` и `admin-api` работают в одном экземпляре; для `admin-api` и `rag-api` задана стратегия обновления `Recreate`.
- Обновление сервера ассистента без простоя: `maxUnavailable: 0`, пробы готовности по `/health`.
- Ограничение памяти и размеров: сервер ассистента 1100 МиБ, `admin-api` 384 МиБ, фото обрабатываются по одному.
- Часовой пояс процессов `Europe/Moscow` определяет границу суток для лимитов.

### 4.4. Совместимость и эксплуатация

- Контракт `admin-api` расширяется только добавлением полей. Исключение: поле `temporary_password` в ответе создания.
- Конфигурация ассистента читается один раз при старте: смена провайдера, моделей и настроек `librechat.yaml` требует перезапуска пода.
- Интерфейс чата и админ-панели адаптирован под русский язык; английский поддерживается.

## 5. Ограничения и допущения

1. Расход ограничивается только суточным лимитом в долларах. Лимиты по числу запросов и месячные лимиты удалены; интерфейс заявок и часть строк локализации ещё упоминают месяц, но сервер принимает только окно `daily`.
2. Курс рубля для провайдера `polza` задаётся вручную переменной `RUB_PER_USD`; прошлые записи журнала не пересчитываются.
3. Стоимость вызова берётся из ответа провайдера; если он её не вернул, запись помечается как стоимость неизвестна и в итоги аналитики не входит.
4. Поддержка форматов документов базы знаний ограничена семью форматами; сканы без текстового слоя отклоняются (OCR нет).
5. Порог релевантности 0,45 подобран экспериментально для модели эмбеддингов `baai/bge-m3`; при смене модели его нужно перемерить.
6. В оверлее `deploy/` эмбеддинги строит локальный сервис (Text Embeddings Inference с той же моделью `baai/bge-m3`), и тексты документов не покидают кластер. Если `rag-api` направлен на внешний провайдер, тексты при индексации уходят к нему (с маскированием DLP при включённом `maskEmbeddings`).
7. Трафик моделей и веб-поиска может идти через внешний прокси; его падение отключает чат целиком.
8. Параллельные вызовы инструментов выключены из-за дефекта сборки потока в используемой библиотеке.
9. Агенты, MCP, расписания, навыки, код-интерпретатор и общие ссылки LibreChat в интерфейсе отключены, хотя код форка их содержит.
10. Синхронизация справочника в базовых манифестах работает в режиме `report` (изменения только протоколируются); оверлей `deploy/` включает режим `apply`, без которого не создаются пользователи по первому входу.
11. Вход по паролю можно временно вернуть аварийным ключом `ALLOW_EMAIL_LOGIN_OVERRIDE` на случай недоступности Keycloak.
12. Расширение magic link для Keycloak (jar) собирается отдельно под используемую версию Keycloak.

## 6. Допущения о внешних сервисах

| Сервис | Допущение |
|---|---|
| Провайдер моделей | OpenAI-совместимый API, возвращает стоимость вызова в поле `usage`; список моделей отдаётся каталогом |
| Keycloak | Realm `corporate`; клиенты: `librechat` (чат), `admin` (админ-панель, публичный, PKCE), `admin-api` (сервисный, роль `manage-users`), `admin-api-notify` (сервисный, без ролей), `ai-admin-api` (сервисный, чтение справочника); у клиента `admin` аудитории `admin-api` и `corporate-ai`, у `admin-api-notify` — `corporate-ai`; загружено расширение magic link |
| Tavily | Ключ задаётся секретом |
| Почта | Письма-приглашения отправляет Keycloak |

## 7. Расхождения и открытые вопросы

- Признак «Руководитель отдела» в справочнике и роль `HEAD` на стороне ассистента не связаны автоматически: синхронизация переносит только признак «Админ». Подсказка в карточке «Настройки AI сотрудника» говорит, что роль задаётся галочками справочника, но в коде этого переноса нет. Ожидаемое поведение (перенос `is_head` в `HEAD`) в текущей версии не реализовано.
- Интерфейс «Сотрудники» доступен только администратору, хотя `admin-api` поддерживает действия руководителя в своём отделе.
